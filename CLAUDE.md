# McSECREtary

AI secretary for Dearborn Denim team — multi-user email triage, daily briefings, dev request queue.

## Tech
- TypeScript (strict), Node.js, SQLite (better-sqlite3)
- Anthropic SDK (`@anthropic-ai/sdk`): model IDs are hardcoded per call site — Haiku for the per-email classifier and cleanup scan, Sonnet for the chat agent, email scan, briefing, reflection, and synthesis. Search for `model:` to find every pin.
- Microsoft Graph API for Outlook email (single Azure AD app, client credentials)
- Grammy (Telegram bot) — single bot, per-user routing by chat_id
- Runs on Railway as persistent service with cron scheduling

## Architecture
- **Multi-user:** `users` table with per-user email accounts, preferences, and briefings
- **Auth:** Single Azure AD app with admin-consented client credentials (reads any mailbox in tenant)
- **Telegram:** One bot, routes messages by chat_id → user_id lookup
- **Dev requests:** Team members submit `/request`, Robert reviews/refines via `/approve`
- **Onboarding:** Admin creates user → generates invite code → user sends `/start <code>` to bot. Full playbook in [ONBOARDING.md](./ONBOARDING.md).

- `/briefing-sections --user=<name> (--set=<csv> | --reset | --list | --diff | --clone-from=<src> | --history [--days=N] | --revert)` OR `/briefing-sections --list` OR `/briefing-sections --set-all=<csv> --apply-to=all` — write, clear, read, diff, clone, view-history, revert, or bulk-set the per-user `briefing_sections_json` preference. When set, that user's daily 5 AM briefing renders ONLY those sections **in the order the array was stored** (e.g., `--set=calendar,stats,emails` renders calendar first, then stats, then emails — overriding the default canonical order). `--reset` clears to NULL (full briefing, default behavior, default order). `--list` (with `--user`) shows that user's stored pref or `(default: full briefing)`. `--list` (bare, no `--user`) shows the canonical catalog of valid section names with one-line descriptions. `--diff` (with `--user`) shows that user's pref vs full briefing — `Current:`, `Missing:`, `Order:` lines (NULL pref → `Current: (default: full briefing)`, `Missing: (none)`); unknown user → `User '<name>' not found. Use /onboarding-status for the list.`. `--clone-from=<src>` (with `--user=<target>`) copies the source user's stored briefing prefs onto the target verbatim — NULL source → resets target to default-full-briefing; unknown source → `User '<src>' not found.`; unknown target → `User '<target>' not found.`; cloning to self → `Cannot clone-from self.`; success → `Cloned briefing prefs from '<src>' to '<target>'. Sections: <csv | (default: full briefing)>`. `--history --user=<name> [--days=N]` lists audit rows for that user newest-first (one line per row: `YYYY-MM-DD HH:MM <action> [from <source_user>] sections=<csv | (default)>`). Days default 7, clamp [1, 90] (audit pruned at 90d). Empty case → `No audit history for '<name>' in last <N> day(s).`. `--revert --user=<name>` undoes the most-recent action by writing the prior `sections_json` from the audit log (the 2nd-most-recent row); writes itself as a new audit row with `action=revert`; <2 rows → `No prior briefing-sections action to revert for '<name>'.`. `--set-all=<csv> --apply-to=all` writes the same section preference to every onboarded (briefing-enabled) user; lists up to 20 names then `...and K more` when >20; `--apply-to` MUST be `all` (anything else is rejected by the parser). Every `--set` / `--reset` / `--set-all` / `--clone-from` / `--revert` write emits a row to `briefing_sections_audit` (auto-pruned >90d on every insert via `BRIEFING_AUDIT_RETENTION_DAYS`, default 90, clamp [1, 3650]); the daily 7 AM CT "Briefing Audit Digest" job summarizes the last 24h of changes (empty case = silent; opt-out via `DISABLE_BRIEFING_AUDIT_DIGEST=1`; recipient configured via `BRIEFING_AUDIT_DIGEST_RECIPIENT`).

## RFQ email — outbound sends and reply intake (spec §12.2–12.4)
The Sourcing agent mails vendors for fabric quotes and the answers come back as product-dev vendor quotes without Robert re-typing anything.

- **Out:** Sourcing files one `rfq_send` proposal per (vendor, run) on the built-in `email` hand (above), subject `[DD-RFQ-<rfq_id>] Fabric request — Dearborn Denim, <season>`, evidence carrying `rfq_id`, `vendor`, `intents` (CSV) and `family`. Level 1, `reversible:false`, `cost_usd:0`.
- **Recognition** (`matchRfqReply`): the `[DD-RFQ-<id>]` tag in the subject or body preview wins (it survives a reply from a different mailbox; the id may contain `.`, `_`, `+` or `-`, matching both Sourcing's `.`-joined and `+`-joined self-test id styles). Otherwise the sender's domain matching an `rfq_messages` row sent within **60 days** — but the domain fallback never fires for a sender on one of our own domains (`resolveOwnDomains`: the `RFQ_MAILBOX`/`RFQ_FROM_ADDRESS` domains plus `RFQ_OWN_DOMAINS`, CSV, default `dearborndenim.com` — a self-test RFQ sent to Robert's own mailbox must never make *other* internal mail from that domain look like a vendor reply), and even for a genuine vendor domain it only fires when the reply also carries the tag (unresolved to a row) or landed in the same Graph conversation as the sent RFQ (`rfq_messages.conversation_id`, populated only when Graph's send returns one — today's plain `sendMail` never does, so in practice this path needs the tag). Anything else takes the ordinary Haiku classifier path.
- **When it runs — three entry points, one intake path (`intakeRfqRepliesFrom` in `src/email/rfq-intake.ts`):** the 30-minute Email Scan job (`handleEmailScan`/`runRfqScan` in `src/index.ts`) runs it over every not-spam message it fetches, so a vendor reply is picked up within 30 minutes rather than waiting on the next 5 AM triage; `runTriage` (`src/triage.ts`) runs it over the triage window at 5 AM / on `briefing`; and the admin-only `scan rfq` Telegram command runs it on demand over the requester's linked accounts (72h window). All three call the same helper — there is exactly one recognition/extraction/filing code path, not three.
- **Idempotency (`rfq_replies` table, `src/db/rfq-queries.ts`):** one row per *inbound* message id, written the moment its intake resolves (whether it filed quotes or only carded an unparsed reply). Any of the three entry points seeing the same inbound message again — the 5 AM triage re-scanning a reply the 30-min job already filed, or two overlapping scans — finds the row and skips it: no double-filed quotes, no duplicate notes card, no second `vendor_quote_received` event. A thrown error from the handler itself (as opposed to an ordinary intake outcome) does **not** mark the row, so a transient failure (product-dev down, DB locked) is retried by the next scan rather than silently dropped.
- **Extraction:** a recognised reply goes to Haiku with `RFQ_EXTRACTION_OUTPUT_FORMAT` (strict JSON: `{options:[{style_number, price_per_yard_usd, weight_oz, width_in, content, moq, moq_unit, lead_days, notes}], unparsed_excerpt}`). Anything the vendor did not state is `null` — the prompt forbids inventing values, and an option with no style number is dropped.
- **Filing:** one product-dev `POST {PRODUCT_DEV_URL}/api/integration/vendor-quotes` per option **per intent on the RFQ** (an RFQ bundles several intents and the vendor does not say which article answers which, so Sourcing ranks per intent in §12.5). Body: `{fabricIntentId, vendorName, description:"<style> — <vendor>", pricePerUnit, unit:"yard", moq, leadDays, priceStatus:"quoted", rfqId, styleNumber, widthIn, weightOz, attachments:[{url,name,kind}]}`. Caps: 10 options × 5 intents, 20 quotes total. `PRODUCT_DEV_URL`/`PRODUCT_DEV_KEY` are the hand's own env vars, reused.
- **Fetch:** `fetchRecentEmails` (`src/email/reader.ts`) takes an `includeBody: boolean = false` 4th arg — off by default (the existing spam-scan/chat-context callers only need `bodyPreview`), on for the Email Scan job and `scan rfq` so the matched-reply extraction has the full stripped body, not just Graph's ~255-char preview. `toRawEmail` adapts the result into the `RawEmail` shape `matchRfqReply`/`processRfqReply` expect.
- **Attachments:** design-module has no asset-upload route and its `/files` is bearer-gated, so McSecretary keeps swatches itself. Graph's attachments API → the volume under `RFQ_FILES_DIR` (default beside the SQLite file, `/data/rfq-files`) → served publicly, unauthenticated, from `GET /files/rfq/<storage_id>/<name>` (mounted in `src/api.ts` before the legacy routes). `storage_id` is 32 random hex chars minted per reply: the path is the capability. Images and PDFs only, inline signature images skipped, ≤8 files of ≤10 MB. With no `PUBLIC_BASE_URL`/`BASE_URL` set the save is skipped and the quotes carry no attachments.
- **Nothing filed:** an out-of-office, a question, or a reply product-dev rejected becomes a `notes` card filed by the system agent id `mcsecretary` (`action_type: rfq_reply_unparsed`, level 1) carrying the excerpt, so the reply never silently disappears.
- **Event:** after at least one quote lands, McSecretary inserts `vendor_quote_received` (urgent) with `{rfq_id, vendor, quotes, intents}` so Sourcing's urgent poll wakes.
- **Acknowledgement** (`sendRfqAcknowledgement`, `src/email/rfq-runtime.ts`): once `processRfqReply` has filed **at least one** quote off the reply, it sends one acknowledgement in the vendor's own thread — plain text, exactly `"Thank you for your response. We have logged your options and will follow up on samples.\n\nDearborn Denim Sourcing"`. Never sent for an unparsed reply (no options, no intents, or every quote rejected) — the gate is simply "filed > 0". Prefers Graph `reply` on the inbound message id (so it lands inline in the thread); falls back to `sendMail` with a `Re:`-prefixed subject and the original `conversationId` when `reply` fails. Sent from the alias per the `email` hand's mailbox/alias split above. Idempotent on the **inbound** vendor message id: `rfq_messages.ack_message_id`/`acknowledged_at` get set on the outbound row `matchRfqReply` resolved, and a re-triage of the same inbound message (restart, retry) is checked against `ack_message_id` first and sends nothing. A failed acknowledgement is recorded in the run's errors but never undoes the filed quotes or the `vendor_quote_received` event.
- The reply is still recorded as a processed email, category `rfq_reply`, urgency `high`, so it shows in the briefing. An intake failure is captured in the run's errors and the email is flagged, never dropped.
- Env: `RFQ_MAILBOX` (the Graph mailbox that sends/receives, default `OUTLOOK_USER_EMAIL_1` else `rob@dearborndenim.com`), `RFQ_FROM_ADDRESS` (the address shown as the sender — an alias of `RFQ_MAILBOX`; defaults to `RFQ_MAILBOX` itself, i.e. no alias), `RFQ_OWN_DOMAINS` (CSV of domains the domain-match fallback must never treat as a vendor, default `dearborndenim.com`; merged with the `RFQ_MAILBOX`/`RFQ_FROM_ADDRESS` domains — see Recognition above), `RFQ_FILES_DIR`, `PUBLIC_BASE_URL`/`BASE_URL`, `RFQ_BRAND_ID` (default `dearborn-denim`), plus the existing `PRODUCT_DEV_URL`/`PRODUCT_DEV_KEY`.

## South Loop Lions schedule checker (`src/lions/`)
Robert coaches the South Loop Lions (CPS SCORE! 7/8th boys, Network 6, Blue Conference). CPS edits game times and opponents in the master Google Sheet without telling anyone, so McSecretary watches it.

## Spine (agent-graph inbox)
McSecretary is the human inbox for the business agents. Agents (Claude Code sessions) file **proposals** over HTTP; McSecretary routes each through the **trust ledger** — execute it against a **hand** (a deterministic service named in `config/brands/<brand>.json`) or send a Telegram card with Approve / Edit / Reject. Hands never call the model; McSecretary never decides on its own.

- Code: `src/spine/` (router, executor, telegram-card + `InboxTransport`, api-routes, jobs, promote-command, wiring, gates, edits, brand-config, agent-keys), `src/db/*-queries.ts` for proposals/trust/events/outcomes/run-index, `src/db/spine-schema.ts`.
- Endpoints: `/spine/proposals`, `/spine/events`, `/spine/events/drain`, `/spine/outcomes`, `/spine/runs`, `/spine/brands/:id`, `/spine/trust`. Auth: `Authorization: Bearer <key>` where the key is listed in `AGENT_KEYS=agent:key,…` — the agent name comes from the key, never from the body.
- `POST /spine/trust/promote` (body `{agent, action_type, level, brand_id?}`, `brand_id` defaults `dearborn-denim`) sets a trust-ledger level outside Telegram/the admin CLI — for a script or a non-Telegram admin surface. Gated by `Authorization: Bearer <SPINE_ADMIN_TOKEN>` (its own env), **not** `AGENT_KEYS` — a valid agent bearer does not unlock it. `SPINE_ADMIN_TOKEN` unset → 503; wrong/missing bearer → 401; unknown brand or a malformed body → 400; a §6 pinned action type above level 1, or a level outside 0–3 → 400 with the same wording as the Telegram `promote` command. Success → 200 with the resulting `trust_ledger` row.
- Read-only hand proxy: `GET /spine/hands/:hand/<path>?brand=<id>&…` forwards the GET to the hand with the hand's bearer (agent never holds it); other query params pass through; non-GET → 405, unknown brand/hand or missing env → 404, path leaving the hand origin (incl. `%2f`/`%2e`) → 400, non-2xx upstream or a body over 1 MiB (streamed, never truncated) → 502 `{hand_status}`; timeout is the hand timeout from wiring (20 s default).
- Pending counts: `GET /spine/events/pending?types=a,b` → `{ counts: { a: { pending, urgent }, … } }` — non-mutating (unlike `/spine/events/drain`); max 50 types of ≤128 chars.
- Proposals accept optional `run_id` (1–128 chars) linking to `agent_run_index.run_id`; stored in `proposals.run_id` (nullable, PRAGMA-gated additive migration in `spine-schema.ts`).
- Human gates in `src/spine/gates.ts` are pinned at level 1 forever. Add an action type there before an agent may use it as a gate.
- Adding a hand: add `{ "url_env", "key_env" }` under `hands` in the brand file and set those env vars on Railway. The executor refuses any path that leaves the hand's origin.
- Built-in `notes` hand: for card-only decisions with no hand to call (capacity warnings, schedule changes, variance reports, restock flags, ...). File `action_payload: { hand: 'notes', method: 'POST', path: '/note', body: { title, summary, notify?, details? } }` — `title` ≤120 chars, `summary` ≤2000 chars, optional `notify` ≤600 chars, optional `details` object. No brand config entry is needed (works for every brand unless it registers its own `hands.notes`, which then wins). The executor never makes an HTTP call for it — it records the body as a 200 response directly — and the Telegram card renders `title`/`summary` in place of the usual `action_type → hand/path` line. `extractNotify` forwards `body.notify`, or `title: summary` when `notify` is absent, into the executed/report message. Because a note is inherently reversible at $0 cost, a level-3 trust promotion on a `notes` action type makes it auto-execute silently (no card, no report) — treat promoting a notes action type to level 3 as "stop telling me about this," not as approving a payment or a write.
- Built-in `email` hand (spec §12.4): the ONLY way a message leaves Robert's Outlook mailbox. File `action_payload: { hand: 'email', method: 'POST', path: '/send', body: { to, cc?, subject, text, html?, attachments?: [{url, name}], rfq_id? } }` — `to`/`cc` take one address or an array (≤10), `subject` ≤120… ≤300 chars, `text` ≤20 000, `html` optional (sent instead of `text` when present), `attachments` ≤5 public http(s) URLs fetched at send time (design-module `/files/...` or our own `/files/rfq/...`), each ≤4 MB; one that 404s or is oversized is skipped and named in the notify line rather than failing the send. No brand config entry is needed (a brand may register its own `hands.email` to override). There is **no HTTP route that sends mail** — a send is always a proposal execution, so the trust ledger (level 1 → Robert taps Approve) has already decided. The Telegram card shows recipient, subject, body and attachment count instead of `action_type → hand/path`. Execution goes out through Microsoft Graph `sendMail` against the **mailbox** (`RFQ_MAILBOX`, default `OUTLOOK_USER_EMAIL_1` else `rob@dearborndenim.com` — `/users/{RFQ_MAILBOX}/sendMail`); when `RFQ_FROM_ADDRESS` names a different address (an alias/shared mailbox), the payload additionally sets `message.from`/`message.replyTo` to that alias (display name "Dearborn Denim Sourcing") so the vendor sees it as the sender while the send still goes out through `RFQ_MAILBOX` — **Exchange must have send-from-alias enabled and the alias must belong to `RFQ_MAILBOX`**, or Graph answers 403/400, in which case the execution error names the alias and mailbox plainly instead of just echoing Graph's text. With no alias configured (`RFQ_FROM_ADDRESS` unset or equal to `RFQ_MAILBOX`), behaviour is unchanged — no `from`/`replyTo` override. Returns `{ok:true, notify:"Sent to <to>: <subject>"}` (the executor forwards `notify`), and records one `rfq_messages` row per recipient. A Graph 4xx marks the proposal `failed` with the status on `execution_result`.
- Built-in `graph` hand (chat → agent-graph router, spec 2026-09-11 §1.3): the third built-in hand, and the only one that **cannot be filed over HTTP** — `validateProposal` rejects `hand: 'graph'` from any agent bearer with a 400, because its only legitimate producer is McSecretary's own chat tool filing in-process through `spine.file`. Payload `{ hand: 'graph', method: 'POST', path: '/dispatch', body: <dispatch plan> }`; the plan shape and its validator live in `src/spine/graph-plan.ts` (`validateDispatchPlan` — expands `line: "both"` into a mens and a womens brief, defaults season to the next season and `target_launch` to 8 weeks out, and bounds the plan: ≤12 briefs after expansion, ≤10 vendor contacts, ≤5 run requests, ≤12 `fabric_locks`, ≤20 `sells`), the hand itself in `src/spine/graph-hand.ts`. The executor makes no HTTP call: it requires `action_type === 'graph_dispatch'` (hand name alone is never authority — any other action type aimed at this hand fails with zero events), re-validates the body so an edited card cannot smuggle a different plan through, and inserts — **inside one `db.transaction` that also writes the proposal's status**, so a throw mid-loop or a row another decision moved leaves zero events — one `design_request` per brief, one `vendor_contact` per contact and one `run_request_<agent>` per run request, all `source_hand: 'mcsecretary'`, `urgent: true`, each carrying `dispatch_proposal_id`. Returns `{ok:true, design_requests, vendor_contacts, run_requests, event_ids}`. `graph_dispatch` is in `PINNED_ACTION_TYPES` (`src/spine/gates.ts`) so it can never auto-execute. The Telegram card renders the plan itself (`GRAPH_PLAN_CAP` 1600, not the 500-char `reason` cap): first line names `evidence.requested_by`, the estimate line comes from `evidence.design_runs_estimated` (falling back to the count in the stored reason), a dispatch of ≤3 briefs also shows a 140-char `brief_text` line per brief, and the Edit hint says only `summary=<new text>` works — `parseEdit` now takes the rest of the line as the value when there is a single `key=` at the start, so a multi-word summary actually applies.
- Chat → graph router (`src/graph/tools.ts`): four **admin-only** chat-loop tools wired in `src/index.ts` via `setGraphDeps` (the `setRfqIntakeHandler` pattern) — `propose_graph_dispatch` (files the pinned level-1 card, stamping `evidence.requested_by`; reads design-module `GET /api/config/personas` for the designer-run estimate, degrading to "per approved persona" when unreachable; reports a de-duped card honestly as already-run or still-waiting rather than "Filed"), `read_agent_outputs` (an agent's newest proposals for the brand plus `latest_run_at`/`stale` at 24 h), `read_hand` (read-only GET, `/api/integration/` paths only, no relative segments, 8 KB cap, the built-in hands are not readable) and `request_agent_run` (one undrained `run_request_<agent>` at a time). `executeTool` passes the calling `userId`; a non-admin (or an unknown user) gets one refusal sentence and nothing is filed. The brand is `GRAPH_BRAND_ID` (defaults to `RFQ_BRAND_ID`, then `dearborn-denim`); the known-agent list is the values of `AGENT_KEYS`, which deliberately excludes `mcsecretary`. The `GRAPH ROUTING` system block (`buildGraphRouting` in `src/chat-prompt.ts`) is appended only for `is_admin` users and governs the four graph tools where the HARD LIMITS paragraph would otherwise forbid agent work.
- `rfq_messages` table (`src/db/spine-schema.ts`, queries in `src/db/rfq-queries.ts`): `{rfq_id, vendor_email, vendor_domain, subject, graph_message_id, sent_at, proposal_id, brand_id, intents, ack_message_id, acknowledged_at}`. `rfq_id` comes from `body.rfq_id`, then `evidence.rfq_id`, then the `[DD-RFQ-<id>]` subject tag; `intents` is the fabric-intent CSV copied from the proposal's `evidence` at send time, and is what the reply's quotes get filed against. Graph's `sendMail` answers 202 with no message id, so `graph_message_id` holds the Graph correlation id (`request-id`, else the `client-request-id` we sent) — reply correlation never depends on it. `ack_message_id`/`acknowledged_at` (additive, PRAGMA-gated) record the acknowledgement sent for a vendor's reply — see below.
- Adding a brand: add `config/brands/<brand_id>.json` (lowercase slug filename = `brand_id`), a user row for its `inbox_user_id` with a linked Telegram chat.
- Executed proposals emit `<action_type>_executed` events for the urgent poll (best-effort, never fails the execution; suppressed for pure-card `notes` proposals whose action type ends `_report`/`_warning`/`_alert`/`_flag`; `sourcing_option` also emits `sourcing_options_executed`).
